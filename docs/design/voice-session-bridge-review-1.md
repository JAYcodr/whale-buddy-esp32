# 第一轮评审综合：小屏语音入口 ↔ DSH 会话桥接

评审对象：[问题陈述](voice-session-bridge-brief.md)
参与：DeepSeek（评审 A）、Kimi（评审 B）、内部（我方）
日期：2026-11-24

> 这份文件只记**分歧与共识**，不复述各自的长论证。原文在两份评审里，需要细节回看原文。

---

## 结论摘要

- **三方一致的第一步**：删掉插件直连 LLM 的那条路，设备改成一个单一专属会话的窗口。
- **两边同时打掉的一个前提**：40 字不是物理上限，而且我们连计量单位都用错了。
- **两份评审共同指出、而文档完全没写的一件事**：没有回执链路。
- **两处真分歧**：设备默认身份（旁观者 vs 遥控器）、路由第一信号（屏幕指针 vs 显式选择）。
- **两边都漏的一件事**：「专属会话凭什么答得出『你在干什么』」。

---

## 一、被两边同时打掉的前提

### 1.1 「40 字」这个数字，两个独立来源都判定为估计值

- 评审 A：98304 字节按 12.3 秒反推是 64 kbps，是**缓冲区常数**，不是发声极限；且 `TTS_MAX_CHARS = 40` 与实际换算的 43–55 汉字互相打架，说明 40 是选出来的，不是推出来的。
- 评审 B：`98304×8/64000 = 12.288s` 只在 64 kbps 前提下自洽；若按 16kHz/16bit 原始 PCM 算只有 3.07 秒。真正脆弱的是**「秒 → 汉字」这一步**——3.5–4.5 字/秒是假设，从来没实测。

**内部核实结论**（已读码确认）：
- 固件 `MAX_TTS_BYTES = 98304` 是单条消息的缓冲上限（`src/net/proto.cpp:268`），不是"不能播更长"。
- 音频队列深 16（`src/hw/audio.cpp:438`），**支持排队**。
- 但每次入队 `++s_voiceGen`，播放前检查 `r.voiceGen == s_voiceGen`——**新语音取消队列里所有旧的**。
- 所以：连发 3 段只会播最后一段。改成"同批共用 voiceGen"约 10–20 行，就能分段播长回复。

**修正**：40 字是**每屏预算**，不是每轮信息预算。屏上 40 字 + 语音可续播，是可行形态。

### 1.2 提示词自身矛盾（评审 B 独家）

prompt 写「屏幕只剩约 3 行」，闸门卡 40 字（≈2 行）。
**发给模型的是 3 行预算，实际执行的是 2 行预算**——模型必然违规，不是模型不听话。

**修正**：预算必须单处定义、两处引用同一个值。

## 二、三方一致（可直接执行）

1. **闸门不能造语义。** 它只能拒绝、截断、标记。"宿主侧规则摘要"是伪解——规则拼不出它不知道的东西。
2. **压缩发生在生成侧，不是截断侧。** 评审核 A 的说法：请求侧就带"一句话答"；评审 B 的说法：把 40 字从"限额"变成"形状"，工具返回 `{结论一句, 还有没有下文}`。两者是同一件事。
3. **闸门必须覆盖所有出站文本**，不只是 `nova_say`。错误提示、确定性摘要、兜底文本都走同一个计量函数——**错误文本最长，最容易被固件整条静默丢弃**（评审 A 独家）。
4. **"在干什么"的投影 schema 不够。** 现在只有 `title/running/lastTool/lastError`，只能答"在不在跑"。最小事实是三元组：**最近一次动作 + 距今多久 + 证据**。
5. **内容相似度不能做主路由信号。** ASR 错字 + 模糊匹配 = 高置信度地进错会话，比随机进错更糟。
6. **设备端的 8 条上限意味着它不该有自己的历史。** 现在插件维护 12 条独立历史，正是"两套历史必然分叉"的根因。绑定后设备应渲染宿主历史的窗口。
7. **模式/目标必须常显**，静默换模式和静默丢 TTS 是同一类失败。
8. **不做兜底截断**（评审 A）：宁可显示"答完了，回 Mac 看"，不要一句被剪断的话。

## 三、两处真分歧（需要拍板）

### 分歧 1：设备默认身份是「旁观者」还是「遥控器」

| | 评审 A | 评审 B |
|---|---|---|
| 默认态 | 旁观者（纯只读） | 看板（纯只读） |
| 升级 | 显式**租约** | 显式切换，模式是**设备端点自身的属性** |
| 失效 | 换段/结束/空闲 10 分钟 → 自动退回**并说出来** | 闲置超时回看板 |
| 措辞差 | "租约有失效条件" | "模式不是会话，是端点的属性" |

**实际差异很小**，只在一点上不同：评审 A 要求**自动退回时必须说出来**，评审 B 只要求模式常显。A 的要求更严，也更对——静默退回等于把显式绑定退化成跟随活跃会话。

### 分歧 2：路由第一信号是「屏幕指针」还是「显式选择」

| | 评审 A | 评审 B |
|---|---|---|
| 第一信号 | **屏幕指针**——设备此刻显示的内容来自哪个会话 | **P0 显式选择**，但做成"长按条目再按住说话" |
| 理由 | 锚在人的感知上："他最后看见的是谁" | 设备自己造一个焦点出来，补上"宿主拿不到 UI 焦点" |
| 内容线索 | 排最后，不做主信号 | P3，只用于重排候选或反问 |
| 硬规则 | — | **自动路由永不指向 running/waiting 的会话**（注入即 steer，往等审批的会话 steer 可能触发意外批准） |

**这两个其实是同一件事的两种实现**：都在说"设备要自己制造焦点"。差别是 A 让焦点**被动产生**（你看过谁），B 让焦点**主动产生**（你按了谁）。

**我倾向 A 为主、B 为升级**：屏幕指针零成本（插件本来就知道自己推过什么），而且"接着弄那个"里的"那个"天然指"我刚在屏幕上看过的"。但 A 的判定需要插件记住"最后一次推给设备的内容来自哪个会话"——一个变量的事。

**B 的硬规则必须采纳**，A 没有覆盖这条，而且它防的是最坏的一种事故：往等审批的会话里 steer，触发意外批准。

## 四、两边都漏的（我方补充）

**专属会话凭什么答得出"你在干什么"？**

两份评审都把"单一专属会话"当成第一步，但都没回答：这个会话的上下文从哪来？

它只有 `nova_sessions()` 的快照（标题 + 状态 + 时间）。所以它答"在干什么"靠的是**读快照**，不是懂。它能接追问、能调工具做行动——这是它的价值，但**它不是主会话的影子**。

这一点必须在产品定位上写死：**专属会话是设备端的代理（agent），不是主会话的镜像**。它的职责是"读仪表盘 + 转达指令"，不是"替你想"。

如果这点不写清楚，后面一定会有人想给它注入主会话的历史——那是最贵的错误。

另外一处（评审 B 独家，我认为成立）：**状态文本一旦作为用户消息进入会话，模型会把它当自己的记忆去行动**——"测试挂了，我来修"，只读查询变成未授权写入。所以状态快照只能作为工具返回值出现，**永不作为用户消息入会话**。

## 五、我的判断与不接受的地方

**接受**：
- 删掉直连 LLM，单一专属会话作为第一步（两方独立同结论，可信度高）
- 闸门放在唯一出站口，覆盖所有文本类型
- 投影改 schema：`{最近动作, 距今, 证据}`
- 状态快照只走工具返回，不走用户消息
- 自动路由不指向 running/waiting
- 回执链路（见下）

**不接受 / 需要打折**：

1. **评审 A 的"不做兜底截断"过于绝对。** 它说宁可显示"回 Mac 看"，但这假设用户此刻能看 Mac。设备的存在意义恰恰是"我不在 Mac 前"。折中：**兜底只推一句模板状态**（"答完了，还没说完"），不推被剪断的正文。既不撒谎，也不让人对着空屏。

2. **评审 B 的"投影 schema 重构"它自己标了'那才是真正的工作量'，但没给优先级。** 我的判断：schema 重构应该在做第二步时一起做，不必单独排期——因为 `nova_sessions()` 一旦上线，schema 就是它的接口，改接口等于改两次。

3. **两份评审都过度聚焦"减少错误"**，没有讨论"这台设备该是什么产品"。合起来它们的潜台词是一致的：**设备是"看板 + 一次投递"的终端，不是聊天客户端**。这和 `page_chat.cpp` 现在的多轮气泡设计有张力——8 条消息、滚动、气泡列表，都在暗示它是个聊天工具。这个张力不解决，工程做得再对，产品还是别扭。

## 六、修正后的最小路径

按"每一步都能单独验证"排：

**第一步（一个周末）**
1. 删 `generateChatReply` 直连路径，`chat_send` 改注入专属会话
2. 专属会话 system prompt：单处定义预算，≤40 字；不允许列点/解释
3. 订阅该会话的 `assistant/message` → 推设备（**先不做工具**，先让链路通）
4. 固件：丢弃超长 TTS 时回一个 `tts_drop` 事件（几十行，把静默失败变可观测）

**第二步（第二个周末）**
5. `nova_sessions()` + `nova_say()` 两个工具
6. 投影 schema 加 `lastAction` / `ageSec` / `evidence`
7. 出站闸门统一计量（按显示宽度，不按字符数）

**第三步**
8. 屏幕指针路由（插件记一个变量）
9. 常显目标会话 + 换段失败时报错不重试
10. 语音分段续播（改 voiceGen 语义）

**明确不做（这一轮）**：多会话切换 UI、小 LLM 摘要、兜底截断正文、语义相似度路由。

## 附：三方对"如果只能做一件事"的回答

- 评审 A：**去掉直连 LLM，单一专属会话**。理由：让问题消失而不是修复它；是唯一能把五条未验证假设变成可测的改动；成本最小可逆。
- 评审 B：**同上，外加固件 TTS 丢弃回事件**。理由：会话错是唯一还在静默损坏数据的错误类；两套大脑并存时任何路由逻辑都是空转。
- 内部：同意。补一条理由——**先接上，才有数据；现在讨论的每一条都是假设**。
