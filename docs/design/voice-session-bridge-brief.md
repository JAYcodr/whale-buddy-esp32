# 问题陈述：小屏语音入口 ↔ DSH 会话桥接

> 给外部评审模型的说明。文中的事实都标了可核对的位置；标「未验证」的是我们的猜测。
> 请**不要迁就下面的方案**，该推翻就推翻。

---

## 0. 一分钟版本

一台 1.8 英寸的桌面小屏设备（带麦克风、扬声器、触摸屏），通过 MQTT 连到一台 Mac，
Mac 上跑着 DeepSeek Harness（DSH，一个 agent 框架）。设备已经能：录音 → 云端 ASR → 显示文字 →
发一句话给宿主 → 收到回复 → 屏上显示 + 语音播报。

现在要把这条链路从「设备自己跟一个小模型聊天」升级成「设备是 DSH 会话的另一个入口」。
升级后卡住的地方不是传输，是三个问题：

1. 设备说的一句话，**该进哪个会话**？
2. 宿主一句 1000 字的回复，**怎么变成屏上的 40 字**？
3. 设备怎么知道「那几个正在干活的会话，此刻在干什么」？

---

## 1. 系统现状（可核对）

### 1.1 硬件与链路

- 设备：Waveshare ESP32-S3 Touch AMOLED 1.8（SH8601 屏 + FT3168 触摸），**368×448 px**，368MB PSRAM。
- 网络：MQTT `mqtt://192.168.31.15:1883`，设备 id `D93468`。
- 上行：`nova/<id>/up`（30s）、`nova/<id>/hello`（retain）。
- 下行：`state / quota / rank / choreo / tts / chat / time`。
- 录音：16 kHz / 16-bit / 单声道 PCM，每包 6 字节小端头 `[clipId:u16, seq:u16, total:u16]` 后跟 PCM，
  topic `nova/<id>/mic/{start|chunk|end}`，QoS 1，每包 2048 字节。
- 插件侧重组分片 → 包 WAV → 送 ASR。

### 1.2 设备端现有交互（`src/ui/page_chat.cpp`）

- 多轮气泡列表，**最多保留 8 条消息**（`MAX_CHAT_MSGS = 8`）。
- 中文 14px 字体，行高 22px，一行约 22 个汉字；气泡区可视约 6–8 行。
- 录音结束后 ASR 文本回填到「即将发送」卡片：**1.5 秒倒计时**，两个按钮「取消重说」「立即发送」。
  超时自动发送。这是现有的「内容确认」环节。
- 快捷指令芯片（几个固定短命令）。

### 1.3 宿主插件现状（`host-plugin/`，约 3000 行 JS）

- 订阅 `session/event`（`global: true`），为每个会话维护一份投影：
  `title / running / waiting / error / lastTool / errMsg / msg / updatedAt`。
  这些字段已用于主屏状态栏、AOD 表盘、审批弹窗。
- 设备发 `chat_send` 事件 → 插件调 `generateChatReply()`（**插件自己直连 LLM API**）
  → 回 `chat { t:'reply' }` + 触发 TTS。
  **这条链路完全绕开了 DSH 会话**：独立历史，12 条滑动窗口，和宿主里那个 agent 不是同一个上下文。
- TTS 播报文本有硬上限：`TTS_MAX_CHARS = 40`，超出直接截断
  （设备侧单条语音 98304 字节 ≈ 12.3 秒 ≈ 43–55 汉字，超了固件会**整条静默丢弃**）。

### 1.4 DSH 平台能力与限制（这部分最关键）

已从源码确认：

| 事实 | 影响 |
|---|---|
| `Agent` 有 `followup(msg) / steer(msg) / inject(msg) / send(msg,target,wakeup) / cancel / whenIdle` | 可以向运行中的会话送用户输入 |
| 更高层入口：`sessionController.prompt({ requestId, sessionId, mode:'queue'\|'steer', content })`，`requestId` 可用于幂等去重 | 适合外部入口，DS-Bot 就这么用 |
| `UserMessage.source` 是可合并扩展的类型（`{ kind: 'user' }` 或自定义 `kind`），**但 provider 适配器只取 `role + content`，source 不进 prompt** | 模型**看不见**结构化来源标记。想让它知道「这条来自设备」，必须写进 content 或用 `inject` 单独送一条 |
| **`sessionId` 不稳定**：上下文压缩会换段，一个逻辑对话可能对应多个 session id。成熟插件（DS-Bot）的做法是绑一个稳定 id，注入前解析到「当前段」 | 设备如果绑死 sessionId，早晚投进已归档的段 |
| **宿主拿不到 UI 焦点**：`activeSession / currentSession / focusedSession` 这类概念在 `dsh-api-session-controller`、`dsh-client-ui-session` 里都不存在 | 无法知道「用户此刻正在看哪个窗口」 |
| 不能在 `session/event` 监听器里调用 `session.append()`（重入守卫），要改挂 `agent/inbox/inserted` | 实现陷阱 |

DS-Bot（同生态的一个成熟插件，把 DSH 会话镜像到手机 App / IM）的做法值得对照：

- 绑 `botId`（≠ sessionId），注入前解析当前段；
- 出站按 `origins: sessionId → chat` 回投；
- `turn/start` 时清 origin，请求没被认领就丢弃，两个来源撞同一 session 标记 `mixed` 并**拒发**；
- 原则写得很直白：**宁可丢，不可串**。

## 2. 要解决的问题

### 2.1 「发错」其实是三种独立的错

| 错误类型 | 现状 | 说明 |
|---|---|---|
| **内容错** | 有防 | ASR 听错字。已用 1.5s 倒计时 + 取消重说兜住 |
| **会话错** | 无防 | 消息进了不该进的会话。真凶 |
| **投递错** | 无防 | 丢包、重复、回复没回来 |

### 2.2 核心难题

> 设备上的一句话，怎么知道该对谁说；
> 宿主的一套长篇推理，怎么变成屏上那句该说的话。

这两个方向不对称：上行缺**路由依据**，下行缺**压缩判据**。

现在设备端的设计里，「聊天」和「看板」其实是两种不同性质的交互，但被塞进了同一个页面：

- 「现在在跑什么」「哪个报错了」→ 需要的是**确定性摘要**，不该走 LLM 自由发挥；
- 「接着弄那个」「帮我看下」→ 需要的是**进入某个会话**，需要明确目标；
- 「你说呢」「讲个笑话」→ 才是真正的对话。

---

## 3. 硬约束（不可动）

1. **单条显示 ≈ 40 字**。超了就滑屏 / 截断，体验崩塌。这个数字和 TTS 的 12.3 秒限制几乎重合，是物理上限不是偏好。
2. **设备端只保留 8 条消息**。不能当聊天记录用，本质是「最近发生了什么」。
3. **宿主无 UI 焦点信号**（见 1.4）。任何依赖「用户正在看的那个窗口」的设计都是空中楼阁。
4. **sessionId 会换段**。任何把 sessionId 当稳定地址的设计都会在某天失效。
5. **`source` 不进 prompt**。模型不会自动知道这条消息来自设备。
6. **TTS 超长 = 静默丢弃**，不是截断、不报错。

## 4. 已评估的方案与各自的死穴

### A. 自动回传全文
宿主 `assistant/message` 全文推到设备。
**死穴**：40 字截断必截错位置。1000 字回复的前 40 字通常是「好的，我来看一下，先梳理一下你的需求」——恰好是最没信息量的部分。只有模型自己知道哪 40 个字是他要的。

### B. 跟随「最近活跃会话」
设备消息自动注入最近有活动的那个会话。
**死穴**：三个窗口并行时无解。而且长任务在跑时，一句语音会 steer 进去打断它。

### C. 工具作为唯一回复通道
模型必须调用 `nova_say(text)` 才能让设备出声。
**价值**：工具是唯一能约束「说什么、说多长」的机制，本质是**输出契约**，不是可靠性手段。
**死穴**：模型忘调就彻底哑。需要兜底，但兜底本身又有事故形态（见第 7 节问题 4）。

### D. 专属会话 + 全局快照
给设备建一个长期会话，注入时附带所有会话的状态快照；它不回任何一个窗口，只回「全局」。
**优点**：零串台；三个窗口共存不冲突；上下文可持续。
**风险**：它是一个「旁观者」，看不见任何一个会话的完整推理，只能看摘要。摘要要是编的，它就撒谎。

### E. 设备端显式绑定
设备上一页会话列表（标题 + 状态点 + 最后活动时间），点一个就绑上。
**优点**：唯一能确定「插进哪个会话」的做法。
**风险**：多一步操作；368px 宽的列表可用性待验。

## 5. 当前倾向（可攻击）

分三层，按「确定性递减」排列：

1. **确定性层**：状态查询类（在干啥 / 报错没）→ 插件直接读会话投影，拼 ≤40 字，不走 LLM。零成本、不撒谎。
2. **会话层**：需要理解或行动的 → 注入专属会话，模型配两个工具：
   - `nova_sessions()` 返回结构化快照（title / running / lastTool / lastReply / ageSec / errMsg）——**给模型事实，不让它编**；
   - `nova_say(text)` 往设备说话，超 40 字直接拒。
3. **兜底层**：turn 结束时该轮没调过 `nova_say` → 取该轮最后一条 assistant 文本压到 40 字，带 `truncated` 标记推过去。

专属会话的 system prompt 目前打算这么写：

```text
你在跟一台 1.8 英寸设备说话，屏幕只剩约 3 行。
- 每条 ≤40 字。超了会被截断，他看不到。
- 只答他问的那一句。不解释、不列点、不用 Markdown。
- 问「在干啥 / 哪一步 / 报错没」先调 nova_sessions()，别凭记忆答。
- 要让他看到听到，必须调 nova_say()。不调 = 他什么也收不到。
```

## 6. 未验证的假设（我们的猜测，请重点打）

1. 模型在 40 字硬约束下的实际合规率——我们没测过。可能大部分回复仍然超长。
2. `nova_sessions()` 返回「标题 + 最近一句 + 状态」是否够模型回答「在干什么」这类问题。标题是 LLM 生成的一句话（如「电量估算四改」），最近一句是 assistant 结尾 120 字。信息量够不够，不确定。
3. 「确定性层」和「会话层」的分界能不能用规则划清。自然语言里「在干啥」和「帮我看看那个」的边界很模糊，规则可能彼此吃掉。
4. 设备端绑定的列表页在 368px 宽的实际可用性——4–6 行、每行标题可能被截断成毫无意义的半句话。
5. 兜底截断（把最后一句压 40 字）会不会造成「看起来像正常回复，其实是废句」的新型误导。

## 7. 请你回答的五个问题

1. **输出闸门放在哪一层？** 是让模型自己用工具压成 40 字（丢给模型的自觉），还是宿主侧做摘要/抽取（丢给规则），还是两个设备（比如手机/电脑）分工不同？有没有第三种做法？
2. **「在干什么」这件事该由谁回答？** 宿主有原始投影（标题、状态、最近工具、最近一句话），设备想要一句话。中间这层压缩，应该是一次小 LLM 调用、规则拼接、还是让主模型带着快照自己说？各自的失效形态是什么？
3. **多会话并存时，设备的「身份」是什么？** 旁观者（看全局摘要）、某个窗口的遥控器（绑一个）、还是两者可切换？如果切换，切换成本应该落在人身上还是系统身上？
4. **「插进某个具体会话」的路由依据，除了设备端显式选择，还有别的可用信号吗？** 已知宿主拿不到 UI 焦点。可用的可能只有：最近有用户输入的会话、最近 turn 结束的会话、标题语义匹配、设备端选择。你怎么排优先级，冲突时怎么裁？
5. **如果只能做一件事**（一个周末、单人、不能改硬件），你会做哪件？为什么它比其他的更值得先做？
